## 尚未完成和必须区分的情况

1. **正式肉鸽 UI 与场景衔接。** 缺少从开局选人、地图选路到奖励、商店、锻造、事件、招募部署及整局结束的可操作界面。`scenes/main.tscn` 仍使用 `BattleSceneCoordinator`，由其直接创建单场 Controller；`GameRoot.start_roguelike_battle()` 和结算信号已存在，但正式场景尚未消费这条 Run 路径。
2. **完整真实通关验证。** `tests/m5_full_run_e2e_test.gd` 创建真实 adapter/controller，但会直接设置 `battle_state["game_over"] = true` 等终局状态。它证明 30 节点的编排与提交边界，不证明真实出牌能击败三章敌人。M4 单场 E2E 也不能替代这一项。
3. **存档与恢复。** Run 虽然 JSON-safe，但未见生产存档读写。需要定义存档版本、自动保存边界、RNG 恢复、奖励/商店权威选项恢复以及异常存档处理；先明确首版是否仅支持节点间保存，避免默认承担战斗中任意时刻恢复。
4. **卡牌版平衡。** 初始牌库、抽牌/SP/能量曲线、重复技能、回手连打、永久成长、遗物组合与三章敌方数值需要真实 Run 样本。当前没有可据以宣称卡牌版平衡完成的证据。
5. **交付收尾。** 完整流程接线后再做新设备启动、导出包、分辨率和正式资源检查；本次未发现导出预设。美术应以 `m4-approved-art-integration.md` 为较新基准，敌方缺失立绘和整体表现验收仍需处理。

## 有意保留的边界，不应误报为漏迁移

- 神通 charge / assault / sacrifice 已迁入休眠模块并有独立测试，但暂不接入玩家流程；两件神通进化遗物继续过滤。后续开放属于新的产品决定。
- 玩家旧式逐弈者行动次数、自由技装备槽、手动大招决策面板由卡牌机制替代，不需要恢复。
- basicDamage 的底层定义与 handler 保留，玩家卡牌目录按已冻结规则排除。
- Run 默认六槽为盾、盾、盾、刺客、弩、旗；直开 M4 战斗仍为 default 六槽。因此打开当前主场景看到普通棋子，不能据此认定 Run 职业投影没有完成。

## 建议后续顺序

以下是新建议的拆分，不是原计划编号的考证结果。

1. **恢复项目总入口并保存当前基线。** 整理现状、决策和剩余规则证据，更新 README，检查并保存 M5 工作树。完成条件：新设备能明确知道工程根、参考 Web 根、当前完成点和下一批工作。
2. **M5.5：肉鸽可玩闭环。** 实现 Run 页面、ViewModel/Command 和场景导航，复用 M5 权威逻辑及 M4 表现。先贯通选人→首战→奖励→地图，再扩展所有节点和三章结局。确保退出/重开、旧战斗清理、动画完成与结算时机正确，避免重复创建会话或结算。
3. **M6-A：节点间存档与恢复。** 优先交付明确保存边界下的继续游戏，覆盖奖励待选、商店已购、RNG 及跨战成长一致性；如需战斗中恢复再单独扩展。
4. **M6-B：真实通关、定向模拟与平衡。** 在不预设胜利的情况下完成三章；记录死亡节点、回合数、卡牌/遗物表现、SP 和能量利用情况。先小样本和针对性检查，再按需要确定批量规模，不自动启动历史 1000 场回归。
5. **可交付版本验收。** 导出包冷启动、继续游戏、完整流程、交互/视觉及必要回归通过后，再对项目整体作最终验收。

首要开发目标：让玩家无需测试脚本，从开局选择弈者，经地图与真实卡牌战斗，领取奖励并进入下一节点。
